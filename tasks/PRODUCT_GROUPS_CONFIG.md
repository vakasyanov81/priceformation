# Контракт конфигурации товарных групп

Решения этапа 1 [плана](PRODUCT_GROUPS_PLAN.md). Это целевая схема; загрузчик
поддерживает объявления групп, отдельные модели их настроек и пять уровней
наследования. Рабочие конфиги и эталоны перенесены в 7.1; в 7.4 временная
совместимость и программный конвертер удалены. Принимается только `product_groups`.

## 1.1. Объявление групп

У поставщика вводится обязательный непустой массив объектов `product_groups`.
Каждый объект одновременно объявляет поддерживаемую группу и содержит настройки
её разбора. Отдельного списка поддерживаемых групп нет. Порядок объектов не
определяет приоритет и назначение входных строк.

| Поле группы | Контракт |
| --- | --- |
| `id` | Обязательная строка из закрытого набора: `tire_and_disk`, `batteries`. |
| `columns` | Отображение входных колонок в поля модели группы. Ключ — индекс XLSX-колонки с нуля либо ключ JSON; допустимые поля задаёт реестр группы. |
| `category`, `title`, `pricing` | Существующие объекты слотов стратегий со своими параметрами. Доступность слотов и стратегий определяет обработчик группы. Обёртка `strategies` не вводится. |
| `behavior` | Настройки обработки группы, включая pipeline. Шинные параметры не становятся обязательными для других моделей. |
| `start_row`, `file_templates` | Настройки чтения для секций группы. |
| `sections` | Обязательный непустой массив секций, принадлежащих этой группе. |

Колонки, настройки чтения и слотов могут быть опущены на уровне группы, если
получены наследованием или заданы секциями. После разрешения настроек секция
должна иметь полный набор для разбора. Порядок наследования фиксируется в 1.2.

`tire_and_disk` отображается как «шины + диски» и включает существующие категории
шин, дисков, камер и лент. `batteries` отображается как «аккумуляторы»; её объявление
разрешено, обработка недоступна до этапа 8. Её поля и стратегии пока не определены.
Идентификаторы чувствительны к регистру и не нормализуются: пробелы, отображаемые
названия и `Tire_And_Disk` недопустимы. Имя листа результата не определяет группу.

На уровне поставщика остаются `code`, `name`, `reader`, `source`; папку определяет
имя JSON-файла. Активация остаётся общей, через `vendor_activation.json`;
отдельного `enabled` у группы нет.

Секция принадлежит группе по вложенности `product_groups[i].sections[j]`;
дополнительного поля `product_group` у секции нет. Сохраняются поля секции `id`,
`name`, `sheet_info`, `sheet_indexes`, `start_row`, `file_templates`, `columns`
и переопределения слотов. Глобальную уникальность `section.id` уточняет 1.7,
маршрутизацию файлов, листов и строк — 1.3.

### Пример одной группы

```json
{
  "code": "demo",
  "name": "Пример поставщика",
  "reader": "xls",
  "source": "file",
  "product_groups": [
    {
      "id": "tire_and_disk",
      "file_templates": ["tires*.xlsx"],
      "start_row": 2,
      "columns": {"0": "title", "1": "price_opt", "2": "rest"},
      "title": {"strategy": "default"},
      "sections": [
        {"id": "demo_tires", "name": "Шины поставщика", "sheet_indexes": [0]}
      ]
    }
  ]
}
```

### Пример двух групп

Аккумуляторные поля и стратегии намеренно не выдуманы. Пример показывает
объявление второй группы, но не является готовым конфигом разбора аккумуляторов.
До этапа 8 выбор обеих групп завершается ошибкой недоступности `batteries` до
чтения файлов, а не молчаливой выдачей только шинного результата (1.5, 4.5).

```json
{
  "code": "demo",
  "name": "Пример поставщика",
  "reader": "xls",
  "source": "file",
  "product_groups": [
    {
      "id": "tire_and_disk",
      "file_templates": ["tires*.xlsx"],
      "start_row": 2,
      "columns": {"0": "title", "1": "price_opt", "2": "rest"},
      "title": {"strategy": "default"},
      "sections": [
        {"id": "demo_tires", "name": "Шины поставщика", "sheet_indexes": [0]}
      ]
    },
    {
      "id": "batteries",
      "file_templates": ["batteries*.xlsx"],
      "sections": [
        {"id": "demo_batteries", "name": "Аккумуляторы поставщика", "sheet_indexes": [0]}
      ]
    }
  ]
}
```

### Валидация

Каждая ошибка содержит имя файла и полный путь до проблемного ключа.

| Вход | Результат |
| --- | --- |
| Нет `product_groups`, значение не массив или массив пуст | Ошибка: требуется непустой список. Старый формат без `product_groups` отклоняется с подсказкой переноса. |
| Элемент не объект | Ошибка с путём `product_groups[i]`. |
| Нет `id`, значение не строка или неизвестно | Ошибка с путём `product_groups[i].id` и допустимыми идентификаторами. |
| Повторный `id` у одного поставщика | Ошибка с обоими путями `product_groups[i].id`; объекты не сливаются. |
| Нет `sections`, значение не массив или массив пуст | Ошибка с путём `product_groups[i].sections`. |
| Чужое поле или стратегия | Ошибка проверки по реестру и слотам группы; реализация в 3.3. |

Одна группа у разных поставщиков допустима. Несколько файлов и листов одной
группы описываются секциями, а не повторением объекта группы. Старую структуру
нельзя молча объединять с новой; переходные правила определяет 3.4.

## 1.2. Наследование настроек

Для каждой секции настройки разрешаются независимо, слева направо; более правый
уровень имеет приоритет:

1. `_common.json.defaults` — общие настройки чтения.
2. `_common.json.product_groups[id].defaults` — общие настройки конкретной группы.
3. `<поставщик>.json.defaults` — общие настройки чтения этого поставщика.
4. `<поставщик>.json.product_groups[id]` — настройки группы у поставщика.
5. `product_groups[id].sections[j]` — настройки конкретной секции этой группы.

Здесь `[id]` обозначает поиск объекта по `id`, а не индекс JSON-массива.
`_common.json.product_groups` также является списком объектов с уникальным известным
`id`, но каждый объект содержит только `id` и `defaults`. Он задаёт значения по
умолчанию и не объявляет группы поставщиков. Отсутствие записи группы в общем
файле означает отсутствие групповых значений по умолчанию.

В новом формате объект `defaults` у поставщика явно отличает общие значения от
старых настроек разбора в корне. Корневые `columns`, `sections`, `category`,
`title`, `pricing`, `behavior`, `start_row`, `file_templates` относятся к старой
схеме; их сочетание с `product_groups` отклоняется по 3.4. `code`, `name`, `reader`
и `source` остаются атрибутами поставщика, не участвуют в слиянии секций.

### Области настроек

| Настройки | Допустимые уровни и правила |
| --- | --- |
| `start_row`, `file_templates` | Все пять уровней; общие для моделей правила чтения. |
| `columns`, `category`, `title`, `pricing`, `behavior` | Только уровни 2, 4, 5: принадлежат конкретной группе. В общих `defaults` уровней 1 и 3 запрещены, даже если поставщик объявил одну группу. |
| `id`, `name` секции | Задаются секцией; `id` не наследуется от кода поставщика или группы. |
| `sheet_info`, `sheet_indexes` | Задаются секцией; не наследуются между секциями. |
| `product_groups`, `sections` | Структурные списки, не настройки для слияния. Общий файл не создаёт группы или секции поставщика. |
| `title_reference_order` в `_common.json` | Существующая настройка выбора названия шин и дисков; не наследуется в настройки других групп. |

Таким образом, шинные значения из текущего `_common.json.defaults` при миграции
переносятся в `product_groups` → `tire_and_disk` → `defaults`. Они не должны
попадать в обработчик аккумуляторов даже временно. Если группе нужен слот,
значение по умолчанию задаёт её собственный контракт, а не соседняя группа.

### Правила слияния значений

| Ситуация | Результат |
| --- | --- |
| Ключ отсутствует на следующем уровне | Сохраняется унаследованное значение. |
| Два объекта | Рекурсивное слияние по ключам, кроме исключений ниже. |
| `columns` | Полная замена карты, без сохранения колонок предыдущего уровня. |
| `markup_rules` внутри `pricing.rules` | Полная замена, как в текущем контракте: шкалы наценок не объединяются. |
| Списки, строки, числа, логические значения | Полная замена; списки не дополняются. `false` и `0` являются явными значениями. |
| Пустой объект | Для обычного объекта не удаляет унаследованные ключи; для `columns` и `markup_rules` заменяет карту пустой. |
| Пустой список или строка | Заменяет значение; допустимость проверяется по контракту поля. |
| `null` или несовместимый тип | Ошибка по пути исходного значения, а не команда удаления или возврата к значению по умолчанию. |

Проверяются структура и типы всех заданных значений, даже переопределённых позднее.
Полнота обязательных настроек проверяется после наследования: например, итоговые
пустые `columns` или `file_templates` недопустимы для файловой секции. Поля и слоты
проверяются по выбранной группе (3.3); запрет обработки ещё не реализованной
группы остаётся отдельной проверкой (1.5, 4.5).

Слияние не изменяет исходные объекты. Изменяемые вложенные структуры результата
не разделяются между секциями, группами и исходными настройками. Сборка одной
секции не должна менять результат следующей.

### Примеры конфликтов

Общий файл целевой схемы:

```json
{
  "defaults": {"start_row": 2, "file_templates": ["*.xlsx"]},
  "product_groups": [
    {
      "id": "tire_and_disk",
      "defaults": {
        "start_row": 3,
        "columns": {"0": "title", "1": "price_opt", "2": "rest"},
        "title": {"strategy": "default", "params_from_title": true},
        "behavior": {"min_rest": 4}
      }
    }
  ]
}
```

Поставщик поверх него:

```json
{
  "code": "demo",
  "name": "Пример поставщика",
  "defaults": {"start_row": 4},
  "product_groups": [
    {
      "id": "tire_and_disk",
      "start_row": 5,
      "title": {"params_from_title": false},
      "sections": [
        {
          "id": "demo_tires",
          "name": "Шины поставщика",
          "start_row": 6,
          "file_templates": ["tires*.xlsx"],
          "sheet_indexes": [0],
          "columns": {"3": "title", "4": "price_opt", "5": "rest"}
        }
      ]
    }
  ]
}
```

Итог секции:

- `start_row` равен `6`: цепочка приоритетов `2 → 3 → 4 → 5 → 6`.
- `file_templates` равен `["tires*.xlsx"]`, общий шаблон `*.xlsx` не добавляется.
- `columns` содержит только ключи `3`, `4`, `5`; ключи `0`, `1`, `2` удалены заменой.
- `title.strategy` остаётся `default`, `title.params_from_title` становится `false`.
- `behavior.min_rest` остаётся `4`, поскольку ни один более высокий уровень его не задал.

Если поставщик дополнительно объявит `batteries`, эта группа получит общие
`start_row: 4` и `file_templates: ["*.xlsx"]`, но не получит шинные `columns`,
`title` или `behavior`. Если секция шин задаст `columns: {}`, это ошибка пустой
итоговой карты, а не просьба восстановить общие колонки. Если она задаст
`title: {}`, стратегия и флаг сохранятся: пустой обычный объект не сбрасывает слот.

При переопределении `title.strategy` остальные параметры объекта сохраняются по
обычным правилам слияния. Итоговый объект должен быть допустим для выбранной
стратегии; несовместимые параметры нужно явно переопределить допустимыми
значениями. Смена имени стратегии не является скрытой операцией очистки объекта.

## 1.3. Маршрутизация входных данных

Маршрут определяется до создания доменной позиции: поставщик → найденный файл →
лист → секция → группа. Файл ищется только в каталоге поставщика по итоговым
`file_templates` секции. Совпадение одного файла с несколькими шаблонами одной
секции не дублирует чтение. XLSX-листы адресуются индексами с нуля;
`sheet_indexes: []` означает все листы. `sheet_info` остаётся описанием, а не
селектором листа. Для JSON нет листов; непустой `sheet_indexes` — ошибка настройки.

Для одного файла разрешены секции разных групп на разных листах. Один физический
лист (для JSON — один входной массив) может обслуживать несколько секций только
с явными селекторами строк у каждой из этих секций. Это правило действует и для
двух секций одной группы: случайное двойное чтение недопустимо.

Вводится объект `row_selector` у секции, который не наследуется. Его форма:

```json
{
  "row_selector": {
    "column": "0",
    "values": ["шина", "диск"]
  }
}
```

`column` — исходный индекс XLSX-колонки в строковом виде либо исходный ключ JSON,
а не имя поля модели. `values` — непустой список уникальных строк; сравнение
точное, чувствительно к регистру, без strip, приведения чисел и распознавания
товара. Отсутствующее, пустое или нестроковое значение не совпадает. В первой
версии нет regex, произвольных выражений и неявного определения группы по полям.
Селектор аккумуляторов может использовать `values: ["аккумулятор"]` той же
входной колонки, не задавая модель аккумулятора.

Секции общего листа должны иметь одинаковый итоговый `start_row`: это единая
граница заголовка и данных. Сначала читаются исходные строки, затем проверяются
все селекторы секций листа, и только после однозначного назначения применяются
колонки и стратегии назначенной секции. Пустые физические строки и строки до
`start_row` не участвуют в маршрутизации.

| Ситуация | Поведение |
| --- | --- |
| Единственная секция листа без селектора | Все строки данных назначаются ей. |
| Строка совпала ровно с одним селектором | Назначается соответствующей секции и группе. |
| Строка совпала с несколькими селекторами | Ошибка маршрутизации: поставщик, файл, лист, номер строки и все конфликтующие секции/группы. |
| Несколько секций листа, хотя бы одна без селектора | Ошибка до обработки строк, даже если секции относятся к одной группе. |
| Разные `start_row` у секций общего листа | Ошибка до обработки строк с путями обеих настроек. |
| Строка не совпала ни с одним селектором | Пропуск с общим счётчиком `unrouted_rows` и предупреждением по файлу/листу; группа строке не назначается. |
| Файл/лист не выбран ни одной секцией | Не обрабатывается, не считается неназначенной строкой. |

Статически обнаружимые пересечения (одна колонка, общие `values`) отклоняются
при проверке настроек. Для разных колонок взаимоисключение проверяется на каждой
строке: порядок секций не разрешает конфликт. Повторные пути к одному файлу
сопоставляются после разрешения пути. Все маршруты поставщика рассматриваются
совместно; фильтрация выбранных секций не должна скрывать неоднозначность.
Выбранная секция обрабатывает только назначенные ей строки.

## 1.4. Контракт шаблона результата

Шаблон имеет стабильный `template_id`, режим `separate_files` либо
`workbook_sheets` и непустой список `groups`. Каждый объект содержит `id` товарной
группы, `sheet_name`, выходные `columns`, `filters`, `formatting`; в режиме
отдельных файлов также `file_name`. В режиме общей книги `file_name` задаётся
только у шаблона (1.6). Это логическое описание контракта, а не требование хранить
существующие Python-шаблоны в JSON.

Выходные колонки задают порядок, поле преобразованной позиции, заголовок,
числовой формат и ширину. Фильтры (включая дубли и склады) и оформление действуют
только на группу объекта. Входные `columns` поставщика никогда не используются
как выходные колонки. Поля, фильтры и преобразователь проверяются по группе.

По умолчанию шаблон должен покрывать все выбранные для вывода группы. Если
внешний шаблон поддерживает только шины и диски, наличие аккумуляторов требует
явного выбора поддерживаемого подмножества вызывающей стороной. Молчаливое
отбрасывание группы запрещено. Этот контракт не вводит новую команду CLI выбора
групп; способ передачи выбора реализуется на этапе 5.5.

| Ситуация | Поведение до записи |
| --- | --- |
| Выбранная группа имеет пустой пакет или опустела после фильтра | Создать файл/лист с заголовками без строк; JSONL — пустой файл с записью схемы в метаданных. |
| Группа отсутствует в выбранном результате | Не создавать её файл/лист, даже если шаблон её поддерживает. |
| Выбранная группа не поддержана шаблоном | Ошибка с `template_id` и группой. |
| Неизвестный или повторный `groups[].id` | Ошибка; определения не сливаются. |
| Нет доступного преобразователя, чужое поле или фильтр | Ошибка с шаблоном, группой и путём настройки. |
| Конфликт файлов или листов | Ошибка по правилам 1.6, без автоматического добавления суффиксов. |
| Не выбрано ни одной группы | Не создавать книги и JSONL, вернуть пустой список выходных файлов. |

Имена листов обязательны в обоих режимах: непустые, не длиннее 31 символа,
без `:`, `\`, `/`, `?`, `*`, `[`, `]`, управляющих символов и апострофа на краях.
В пределах одной книги имена уникальны без учёта регистра; зарезервированное
Excel имя `History` отклоняется без учёта регистра. Некорректные имена не обрезаются
и не исправляются автоматически. Состояние форматирования и записи строк
изолировано по листам; книга сохраняется после заполнения всех её листов.

## 1.5. Граница поддержки аккумуляторов

Известный идентификатор и доступная обработка — разные проверки. `batteries`
разрешён в декларации поставщика; это не разрешает создавать для него `RowItem`,
вызывать шинные стратегии или молча исключать группу из результата.

До чтения любого прайса и до создания выходных файлов выполняется preflight для
всего выбранного запуска: наличие обработчиков, фабрик, стратегий и выходных
преобразователей. До завершения этапа 8.6 выбор `batteries` завершает весь запуск ошибкой
`unsupported_product_group` с именем поставщика, группой и путём
`<файл> → product_groups[i].id`, например:

> Поставщик demo: группа batteries объявлена, но её обработка ещё не реализована.

Декларацию можно просматривать командами схемы и настроек без запуска обработки.
Проверка недоступности обработчика предшествует проверкам обязательных полей
модели: отсутствие аккумуляторных колонок в декларации не должно маскировать
причину отказа. Структура декларации, известность идентификатора
и уникальность секций проверяются всегда. До этапа 8 многогрупповые сценарии
инфраструктуры проверяются тестовой второй моделью из 7.2, отсутствующей в приложении.

В этапах 8.2–8.3 реализованы отдельная модель и обработка позиций.
Допускаются собственные аккумуляторные колонки и слоты:

```json
{
  "title": {"strategy": "plant", "lines": ["XTREME +EFB", "XTREME Arctic"]},
  "pricing": {"policy": "recommended"},
  "behavior": {"rest": "count", "min_rest": 1}
}
```

Это значения по умолчанию аккумуляторной секции. Линейки перечисляются явно;
пустые и повторяющиеся названия запрещены. Цена продажи равна РРЦ, без наценки
на закупочную. Нет РРЦ или подтверждённого остатка от одной штуки — позиция
исключается с диагностикой. Неизвестная или неоднозначная линейка — ошибка.
Шинные слоты и поля отклоняются при загрузке. Для создания обработчика нужны
отображённые `code`, `title`, `price_recommended`, `rest_count`; при просмотре
декларации без запуска колонки могут отсутствовать. Детали контракта —
[BATTERIES_MODEL.md](BATTERIES_MODEL.md).

После 8.6 снимается только запрет для реализованной группы `batteries`; общая
preflight-проверка остаётся для любого выбранного набора групп.

## 1.6. Имена файлов

В `separate_files` имя задаёт каждый объект группы; общего `file_name` нет.
В `workbook_sheets` имя задаёт шаблон; у объектов групп `file_name` запрещён.
Пример размещения двух групп после этапа 8 (колонки, фильтры и оформление опущены):

```json
{
  "template_id": "inner",
  "mode": "separate_files",
  "groups": [
    {"id": "tire_and_disk", "file_name": "price_tire_and_disk_{now}.xlsx", "sheet_name": "шины + диски"},
    {"id": "batteries", "file_name": "price_batteries_{now}.xlsx", "sheet_name": "аккумуляторы"}
  ]
}
```

```json
{
  "template_id": "inner",
  "mode": "workbook_sheets",
  "file_name": "price_{now}.xlsx",
  "groups": [
    {"id": "tire_and_disk", "sheet_name": "шины + диски"},
    {"id": "batteries", "sheet_name": "аккумуляторы"}
  ]
}
```

`{now}` — дата `YYYY-MM-DD` в локальном часовом поясе, фиксируемая один раз на
запуск. Другие подстановки, спецификаторы формата и неизвестные поля запрещены.
Имя — только имя файла с расширением `.xlsx`, без директорий, абсолютных путей,
`..`, разделителей `/` и `\`, управляющих символов и символов `<>:"|?*`;
недопустимы конечная точка/пробел и зарезервированные имена устройств Windows.
Файлы размещаются в каталоге результатов.

JSONL всегда разделяется по группам. Для отдельных книг расширение собственного
имени заменяется на `.jsonl`. Для общей книги к основе добавляется `_{group}`:
`price_2026-11-11_tire_and_disk.jsonl`, `price_2026-11-11_batteries.jsonl`.

До первой записи строится общий план всех выбранных шаблонов и форматов с уже
подставленной датой. Проверяются все пути XLSX, JSONL и `result_meta.json`;
разные определения не могут писать один путь. Для переносимости сравнение имён
выполняется без учёта регистра. Например, `price_{now}.xlsx` и
`price_2026-11-11.xlsx` конфликтуют при запуске 2026-11-11. Листы разных групп
одной общей книги — один запланированный файл, а не конфликт путей.

Существующий результат того же шаблона и группы можно заменить при повторном
запуске после проверки совместимости метаданных по 1.8. Это не разрешает двум
определениям текущего плана использовать один путь. Исторические имена файлов
существующих шаблонов сохранены при миграции 7.1.

## 1.7. Идентичность секций

`section.id` — явный непустой строковый внешний ключ CLI, каталогов поставщиков
и отчётов. Его значение сохраняется при переносе старых конфигов. Ключ не
дополняется идентификатором группы и не выводится автоматически из `vendor.code`.
Сравнение точное, без нормализации; пробелы по краям запрещены.

До построения реестра и каталогов загружается полный набор конфигов поставщиков,
включая отключённых и не выбранных для разбора. `section.id` должен быть уникален
во всём наборе, независимо от поставщика и группы. Ошибка указывает значение
ключа и оба места, например:

> Повтор section.id 'demo_tires': vendors/a.json → product_groups[0]
> (tire_and_disk) → sections[0].id и vendors/b.json → product_groups[1]
> (batteries) → sections[2].id.

Порядок загрузки не определяет победителя: запись не перезаписывается. Отключение
поставщика не исправляет конфликт. Общие defaults не объявляют секций и в эту
проверку не входят. Формат без `product_groups` отклоняется при загрузке;
неявные ID секций из кода поставщика больше не подставляются.

Внешний ключ группы дублей — пара `(product_group, local_group_id)`; например,
`(tire_and_disk, 7)` и `(batteries, 7)` различны. Этот ключ не заменяет `section.id`.

## 1.8. Машинные форматы v2

### CLI JsonReport

После перехода каждый `JsonReport` имеет `version: 2`, включая одну группу,
пустой запуск и ошибки. Поля `ok`, `action`, `warnings`, `files`, `suppliers`,
`disabled_suppliers`, `error` сохраняются. Корневого `positions` больше нет;
`groups` отображает идентификатор группы в объект ровно с `positions` и `stats`.
Позиции сериализуются преобразователем собственной модели.

Выбранная группа присутствует даже при нуле позиций. Не выбранная группа не
включается. При ошибке до определения выбора `groups` равен `{}`; при известном
выборе содержит выбранные группы с пустыми позициями. Ошибка всего запуска
задаётся `ok: false` и `error`, поэтому пустая успешная группа и отказ различимы.
Частичные позиции и файлы при ошибке разбора не публикуются как успешный результат.
Без запроса полного результата `positions` внутри групп пусты, а статистика
сохраняет реальные значения — как в нынешнем режиме отчёта только статистики.

Общие `stats`: `items`, `priced_items`, `doubles`, `black_list_skips`,
`unrouted_rows`, `elapsed_seconds`. Первые четыре счётчика суммируются по группам;
`unrouted_rows` считается до назначения группы, время — длительность всего запуска,
а не сумма времени групп. Групповые `stats` содержат общие для позиций счётчики
`items`, `priced_items`, `doubles`, `black_list_skips` и специфичные счётчики модели.
Шинные `unknown_category_skips`, `type_corrections`, `title_conflicts`,
`percent_markup`, `absolute_markup` остаются только в `tire_and_disk.stats`.
Статистика аккумуляторов определяется на этапе 8; шинные поля ей не приписываются.
Предупреждения групп содержат идентификатор группы и контекст поставщика/секции.

Ниже полные примеры оболочки; специфичные счётчики группы сокращены до общих.
Пример двух групп описывает будущий успешный результат после этапа 8.

```json
{
  "ok": true,
  "version": 2,
  "action": "parse",
  "groups": {
    "tire_and_disk": {
      "positions": [],
      "stats": {"items": 0, "priced_items": 0, "doubles": 0, "black_list_skips": 0}
    }
  },
  "stats": {"items": 0, "priced_items": 0, "doubles": 0, "black_list_skips": 0, "unrouted_rows": 0, "elapsed_seconds": 0},
  "warnings": [],
  "files": [],
  "suppliers": {},
  "disabled_suppliers": {},
  "error": null
}
```

```json
{
  "ok": true,
  "version": 2,
  "action": "parse",
  "groups": {
    "tire_and_disk": {"positions": [], "stats": {"items": 0, "priced_items": 0, "doubles": 0, "black_list_skips": 0}},
    "batteries": {"positions": [], "stats": {"items": 0, "priced_items": 0, "doubles": 0, "black_list_skips": 0}}
  },
  "stats": {"items": 0, "priced_items": 0, "doubles": 0, "black_list_skips": 0, "unrouted_rows": 0, "elapsed_seconds": 0},
  "warnings": [],
  "files": [],
  "suppliers": {},
  "disabled_suppliers": {},
  "error": null
}
```

При отсутствии выбранных групп успешный ответ имеет `groups: {}`, нулевые общие
счётчики и `files: []`. Пример ошибки до определения выбора:

```json
{
  "ok": false,
  "version": 2,
  "action": "parse",
  "groups": {},
  "stats": {"items": 0, "priced_items": 0, "doubles": 0, "black_list_skips": 0, "unrouted_rows": 0, "elapsed_seconds": 0},
  "warnings": [],
  "files": [],
  "suppliers": {},
  "disabled_suppliers": {},
  "error": {"kind": "config_validation", "message": "Повтор section.id: demo_tires"}
}
```

### JSONL и result_meta.json

`result_meta.json` имеет корневые `version: 2` и `files`. Ключ `files` — путь JSONL
относительно каталога результатов с разделителем `/`, без выхода за каталог.
Значение — `template_id`, `product_group`, `schema_version`, `columns`,
`value_codes`. `schema_version` — положительная целая версия схемы пары
«шаблон — группа», не версия оболочки метаданных. Начальная версия схемы — 1;
изменение смысла колонок требует её повышения.

`columns` отображает компактный числовой строковый ключ в имя выходной колонки.
`value_codes` — локальная для файла карта «код → исходное значение».
Сохраняется компактная форма кодов `@N`, где N — положительное целое число.
Исходные строки, совпадающие с кодом, не должны становиться неоднозначными:
такой код нельзя назначать другому значению. Поля названия не кодируются,
как и в текущем JSONL; сведения о полях названия даёт преобразователь группы.
Числовые ключи и коды локальны файлу, не сравниваются между файлами и запусками.
Порядок колонок задаётся возрастанием числового ключа. Не включённые в JSONL
выходные колонки (например, служебные пропущенные) не попадают в схему.

Пример реестра двух файлов после этапа 8; `battery_label` — условное имя выходной
колонки для иллюстрации независимости схем, а не утверждённое поле модели:

```json
{
  "version": 2,
  "files": {
    "price_2026-11-11_tire_and_disk.jsonl": {
      "template_id": "inner",
      "product_group": "tire_and_disk",
      "schema_version": 1,
      "columns": {"1": "title", "2": "season"},
      "value_codes": {"@1": "Зимняя"}
    },
    "price_2026-11-11_batteries.jsonl": {
      "template_id": "inner",
      "product_group": "batteries",
      "schema_version": 1,
      "columns": {"1": "battery_label"},
      "value_codes": {"@1": "Условное значение"}
    }
  }
}
```

Строки этих двух файлов могут иметь вид `{"1":"Пример шины","2":"@1"}` и
`{"1":"@1"}` соответственно: один код `@1` означает разные вещи по пути файла.
Для одной группы реестр содержит одну запись; для пустой выбранной группы
создаётся пустой JSONL и полноценная запись схемы с `value_codes: {}`, если кодов
нет. Без выбранных групп JSONL и метаданные не создаются.

До записи проверяются существующие метаданные. Старый общий словарь v1 (включая
формат без явного `version`), неизвестная версия, повреждённый JSON и смесь
структур v1/v2 отклоняются с путём и требованием пересоздать результат. Файлы
текущего запуска не изменяются до успешного завершения этой проверки.
Существующий JSONL без записи в корректном реестре также нельзя молча принять
или дописать. Несовпадение `template_id`, группы или `schema_version` существующей
записи с планом требует пересоздания результата.

Повторный запуск заменяет JSONL и его запись схемы совместно, без дописывания строк
и переиспользования старых кодов. Записи других файлов v2 сохраняются; кодовые
таблицы одного файла не расширяют таблицы другого. Метаданные не должны
публиковать новую схему для ещё не заменённого файла.

### Миграция потребителей и проверяемые сценарии

Автоматической выдачи v1 и неявного объединения моделей нет. Потребитель сначала
проверяет `version == 2`, затем читает `groups[id].positions` и `groups[id].stats`
вместо корневого `positions` и шинных счётчиков общей статистики. Отсутствие ключа
группы отличается от пустого списка; при `ok: false` обрабатывается `error`.
Потребитель JSONL выбирает схему исключительно по относительному пути в `files`,
затем декодирует значения по локальному `value_codes`, исключая поля названия.

Для миграции результата v1 нужно сохранить нужные старые файлы отдельно, очистить
или выбрать новый каталог результата и повторно сформировать JSONL вместе с
метаданными v2. Простое добавление `version: 2` к старому словарю запрещено.

При реализации 5.5 и 6.7 обязательны тесты:

- Одна и две группы, включая непустые позиции разных моделей (до этапа 8 — тестовая модель 7.2).
- Пустая выбранная группа, отсутствующая группа и полностью пустой результат.
- Ошибка до определения выбора и ошибка известной группы; всегда `version: 2`.
- Режим только статистики сохраняет группы и реальные счётчики без позиций.
- Суммирование общих счётчиков без шинных полей аккумуляторов.
- Одинаковые ключи колонок и коды с разными значениями в двух JSONL-файлах.
- Оба способа именования JSONL, пустой файл со схемой и конфликты путей до записи.
- Отказ для v1, смеси версий, повреждённых метаданных и несовместимой схемы без изменения файлов.
- Повторная запись одного файла v2 сохраняет независимую схему другого.


## Переход конфигов завершён (7.4)

В этапах 3.4–7.1 временный модуль `parsers.vendor_config.migration` помог перенести
рабочие файлы и эталоны без изменения настроек. В 7.4 модуль, его тесты и загрузчик
старой схемы удалены; автоматического преобразования при запуске нет.

Оставшийся сторонний старый конфиг нужно перенести явно:

1. Поместить настройки чтения, колонки, стратегии и `sections` в объект
   `product_groups` с `id: "tire_and_disk"` по примерам 1.1.
2. Задать каждому разделу явный строковый `section.id`, уникальный во всём
   наборе поставщиков. Сохранить внешние ключи CLI и каталогов.
3. В `_common.json` оставить в общих `defaults` только `start_row` и
   `file_templates`, а модельные настройки перенести в `product_groups[].defaults`.
4. Если есть блок `api`, отдельно перенести его группы и настройки чтения:
   они не наследуются от файлового варианта.

Ошибка старого поставщика указывает файл, `product_groups`, группу
`tire_and_disk` и необходимость явных ID секций. Модельные общие `defaults`
отклоняются с путём до ключа и указанием `product_groups[].defaults`.
Смешение плоских и групповых настроек по-прежнему запрещено.

В 7.1 пользовательские файлы и оба набора эталонов перенесены в новый формат.
У Форточек согласованы ID `5` (шины) и `55` (диски) для обоих источников;
у МИМ — `4`, `42`, `43` в порядке вкладок. Имена выходных файлов и листов сохранены.
Старый загрузчик исправлен: `behavior` наследуется секциями с их собственными
переопределениями. Сравнение миграции выполняется после этого исправления;
настройки, ранее игнорировавшиеся из-за ошибки, теперь применяются.


## Просмотр поставщиков и схемы (3.5)

Команды `get_vendors --json` и `toggle_vendor <folder> --json` возвращают
`product_groups` — список стабильных идентификаторов объявленных групп поставщика.
Объявление `batteries` видно без запуска её обработчика. Меню активации показывает
отображаемые названия групп рядом с поставщиком; переключение действует на всего
поставщика и сохраняет только его статус в `vendor_activation.json`.

Контроль схем прайсов после обновления обходит секции каждой группы, используя
её собственные шаблоны файлов и индексы листов. Предупреждение содержит название
и идентификатор группы. Для `tire_and_disk` сравниваются также используемые
колонки; для `batteries` до определения модели проверяются только листы XLSX.

## Внутренняя статистика и диагностика (5.4)

`ParseResult.statistics` адресует общие счётчики через `ProductGroup`:
число позиций (`item_count`), позиций с ценой (`priced_items`), дублей (`doubles`)
и пропусков чёрного списка (`black_list_skips`). Для шин и дисков счётчики позиций
заполняются после группировки. `total_statistics()` считает итоги только выбранных
пакетов; число позиций берётся из самих пакетов, без обращения к полям их моделей.

`tire_and_disk_diagnostics` отдельно хранит неизвестные категории с названием
поставщика, исправления типа, конфликты и несобранные названия, исправленные
и подозрительные двойники алфавитов. Эти счётчики не переносятся в другую группу.
Диагностика секций суммируется без разделения изменяемых списков с парсером.

`ParseResult.unrouted_rows` — общий счётчик до назначения группы: несколько
выбранных секций с одним `VendorRouting` учитывают его ровно один раз.
Сводки, предупреждения JSON и ошибки разбора включают стабильный идентификатор
группы; сообщения конкретного парсера сохраняют контекст поставщика и секции.
Это внутренняя подготовка формата v2; внешняя оболочка JSON меняется в 5.5.

## CLI JSON v2 (5.5)

Команды `parse --json` и `doubles --json` используют оболочку версии 2 из 1.8.
`groups` строится по выбранным пакетам, включая пустые; позиции преобразуются
собственным сериализатором модели пакета. Без `--all-result` позиции не
сериализуются, статистика групп и общие итоги сохраняются. В отчёте дублей
фильтрация позиций не меняет статистику полного разбора.

Определённый выбор групп сохраняется до сборки парсеров. При ошибках сборки,
чтения, группировки или записи ответ содержит выбранные группы с пустыми
позициями и нулевые общие счётчики, `files: []`, `ok: false` и `error`.
Если загрузка конфигурации не позволила определить выбор, `groups: {}`.
Без выбранных групп писатель не запускается и файлы не создаются.

Потребители должны проверять `version == 2` и читать `groups[id].positions` /
`groups[id].stats`; корневого `positions` и шинных полей общей статистики больше
нет. Примеры и миграция описаны в README. Тестовая вторая модель проверяет
независимость схем JSON без включения обработки аккумуляторов в приложение.
JSONL также использует реестр метаданных v2; реализация описана в 6.7 ниже.


## Описание выхода в Python-шаблонах (6.1)

`IWriteTemplate.output_spec()` возвращает `TemplateOutput` из
`parsers/writer/templates/group_output.py`: `template_id`, `mode`, кортеж
`groups` и необязательное имя общей книги. `GroupOutput` содержит `id`,
`sheet_name`, выходные `columns`, `filters`, `formatting`, `merge_warehouses`
и необязательное имя отдельной книги. `schema_version` — положительное целое
число (по умолчанию 1), версия схемы пары шаблон–группа в JSONL. Оформление и колонки сохраняют существующий
формат Python-шаблонов, включая форматы и ширины колонок.

Текущие `for_inner`, `for_drom`, `for_full` и `for_doubles` объявляют стабильные
ID, совпадающие с именами CLI. Их описание содержит одну группу `tire_and_disk`
в режиме `separate_files`; прежние имена файлов и лист `price` сохранены.
Описание получает независимые копии вложенных настроек. Входные колонки
поставщика не используются. Многогрупповой шаблон переопределяет `output_spec`.
Проверка описания и переход записи на него выполняются в 6.2–6.7.

## План записи (6.3)

`prepare_output_plan` из `parsers.writer.output_plan` принимает описания шаблонов
и связанные с пакетами преобразователи `GroupOutputSource`. Преобразователь
объявляет допустимые поля и скрывает модель позиции за `prepare`: правила
складов, дублей и фильтры выполняются внутри группы до сериализации.
Для шин и дисков используется `TireOutputSource` с `TireAndDiskResult`
и настройками дублей; порядок — склады, дубли, фильтры, выходные поля.

По умолчанию выбраны все переданные пакеты; `selected` позволяет явно сузить
выбор, включая пустой набор. Пустой выбранный пакет сохраняет лист, отсутствующая
в выборе группа не создаёт книгу или лист. Все описания и пути проверяются
до вызова первого преобразователя. Дата определяется один раз, настройки
копируются независимо от исходных шаблонов.

Результат — кортеж `WorkbookPlan`: имя книги, ID шаблона и листы `SheetPlan`
со своими настройками и выходными полями. Режим `separate_files` создаёт
по плану книги на группу; `workbook_sheets` собирает листы одного шаблона
в одну книгу. Планирование не читает и не записывает файлы; подключение
к существующим писателям выполняется в 6.4–6.7.

## Отдельные XLSX-файлы (6.4)

`GroupFileWriter` из `parsers.writer.group_files` принимает описания шаблонов,
связанные с пакетами преобразователи и необязательный явный выбор групп.
Весь план проверяется и подготавливается до создания первого драйвера.
Для каждой группы в `separate_files` создаётся отдельная книга с её `file_name`,
именем листа, колонками и оформлением. Возвращаются абсолютные пути всех книг
в порядке шаблонов и групп. Пустая выбранная группа создаёт книгу с заголовками;
пустой выбор не создаёт каталог. Конфликт итоговых путей отклоняется до записи,
включая случай уже существующего файла.

`SheetTemplate` передаёт готовые настройки в `XlsWriter`: фильтры уже применены
к доменным позициям, имя файла уже содержит дату. Повторная фильтрация выходных
словарей и повторная подстановка даты для планового XLSX не выполняются.
Старый API писателя по классу шаблона сохранён. `CommonPriceOut` использует
групповой план для текущей группы шин и дисков и одну дату для всех XLSX одного
вызова, включая отчёт дублей. Фабрики записи находятся в `writer.factories`.

Две независимые книги проверяются на `RowItem` и тестовой `TestPosition`,
которая существует только в тестах. Это не разрешает разбор аккумуляторов.
Режим `workbook_sheets` подключён в 6.5–6.6; JSONL v2 подключён в 6.7.


## Предварительная проверка шаблонов (6.2)

`parsers.writer.output_validation.validate_outputs` получает описания шаблонов
и явный набор выбранных групп. Каждая выбранная группа должна быть объявлена
каждым выбранным шаблоном. Чтобы использовать внешний шаблон с меньшим набором,
вызывающий код должен явно передать поддерживаемое подмножество.

Проверка использует схемы доступных выходных преобразователей (`schemas`):
по умолчанию доступна только схема `tire_and_disk` из реестра `RowItem`.
Колонки (`field`, `suffix_when`), фильтры и правила цвета (`by_column`)
проверяются по схеме своей группы. Отсутствующий преобразователь отклоняется.
Имена и структура проверяются также у объявленных невыбранных групп;
в конфликтах путей участвуют только выбранные группы.

Дата подставляется один раз на вызов проверки; проверяются пути XLSX и JSONL
с учётом обоих режимов размещения. Общая книга допускает один путь для своих
листов, но JSONL каждой группы остаётся отдельным. Имена сравниваются без учёта
регистра. Ошибки `ConfigValidationError` содержат шаблон, группу и путь настройки.
`CommonPriceOut` проверяет все выбранные шаблоны вместе с отчётом дублей до
первой записи. Построение и исполнение плана по этому описанию — этапы 6.3–6.7.


## JSONL и метаданные v2 (6.7)

`GroupFileWriter.write(as_jsonl=True)` использует тот же проверенный план,
что XLSX, но создаёт отдельный поток для каждого листа группы. Режим размещения
сохраняется в `WorkbookPlan`, поэтому даже одна выбранная группа общей книги
получает суффикс группы в имени JSONL. `GroupOutputSource.title_fields`
объявляет поля названия, исключаемые из кодирования, без знания шинной модели
в общем сериализаторе.

`jsonl_writer.write_plan_jsonl` подготавливает строки и локальные схемы всех
потоков. `jsonl_meta` проверяет полный существующий реестр и принадлежность
перезаписываемых файлов до изменений. Пустые группы сохраняют схему и пустую
карту кодов; пустой выбор не создаёт метаданные. Коды назначаются заново для
каждого файла и запуска; исходные строки вида `@N` резервируют соответствующий
код. Старые общие метаданные не принимаются и требуют пересоздания результата.

`jsonl_publish` сначала записывает временные файлы в каталоге результата,
заменяет потоки, затем реестр. При ошибке замены восстанавливает заменённые
файлы и удаляет новые. Это восстановление при ошибке ввода-вывода, а не
транзакция при аварийном завершении процесса или параллельных запусках.
`CommonPriceOut` готовит потоки всех выбранных шаблонов и отчёта дублей перед
единой проверкой реестра и публикацией. Преобразования складов, дублей и фильтров
выполняются до JSONL так же, как перед XLSX. Миграция потребителей описана
в README; тесты — `test_group_jsonl.py`, `test_jsonl_writer.py`,
`test_common_price_output.py` и эталонный `test_row_item_golden.py`.
