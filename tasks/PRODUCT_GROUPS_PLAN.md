# План: товарные группы поставщиков и раздельные модели позиций

## Цель

Поставщик объявляет список товарных групп и настраивает для каждой входные колонки и стратегии. Результат разбора содержит отдельные типизированные списки позиций. Шаблон результата определяет, записывать группы в разные файлы или на отдельные листы одной книги.

Начальные группы: `tire_and_disk` — «шины + диски», `batteries` — «аккумуляторы». Товарная группа — отдельное понятие: существующие категории шин, дисков, камер и лент остаются внутри `tire_and_disk`.

## Исходные места изменений

- `src/parsers/vendor_config/models.py`, `slot_configs.py`, `merge.py`: настройки поставщика, секции и наследование.
- `src/parsers/base_parser/config_driven_parser.py`: сейчас адаптер строки жёстко задан как `RowItem`, стратегии собираются для текущей модели.
- `src/domain/row_item/`: существующая модель шин и дисков, реестр полей и преобразования.
- `src/services/parse_orchestrator.py`, `parse_result.py`: сбор общего списка и запуск группировки.
- `src/parsers/common_price/`: группировка дублей, выбор главного предложения, склады, названия и подготовка вывода.
- `src/parsers/writer/`: шаблоны, XLSX/JSONL и драйвер книги. Сейчас `XlsWriter` создаёт один лист `price`, а `XlsxWriterDriver.add_sheet()` переименовывает активный лист.

## Проектные правила

- У каждой группы своя модель позиции и свой реестр допустимых полей. Не добавлять аккумуляторные поля в существующий `RowItem`.
- Общими делать только подтверждённые общие понятия. Не проектировать характеристики аккумулятора до появления требований.
- Один пакет результата содержит позиции одной группы и одной модели. Общий результат объединяет пакеты, а не строки разных моделей в один плоский список.
- Состав групп поставщика не определяет размещение результата: размещением управляет шаблон вывода.
- Общий оркестратор работает через интерфейс обработки группы; конкретные стратегии, модель, правила дублей и преобразование в выходные поля скрыты в реализации группы.
- Группы изолированы до преобразования позиций в данные для записи. Плоские словари допустимы на выходе в writer, но не заменяют доменные модели внутри разбора.
- Сохранять существующие направления зависимостей; реализации и фабрики собирать в композиционном корне.

## Этап 8. Полноценная поддержка аккумуляторов — после определения модели

Этот этап зависит от отдельных требований к аккумуляторам. Этапы 1–7 подготавливают инфраструктуру и сохраняют работу шин и дисков, но не означают готовность разбора аккумуляторов.

- [ ] **8.1. Определить модель аккумулятора.** Согласовать поля, типы, единицы измерения, обязательность, инварианты, идентичность товара и правила отображения. Не включать предполагаемые характеристики в текущую реализацию заранее.
- [ ] **8.2. Реализовать отдельную доменную модель и реестр полей.** Добавить преобразования и проверки на входе; доказать отсутствие зависимости от шинной модели.
- [ ] **8.3. Реализовать аккумуляторные стратегии и обработчик группы.** Добавить специфичные слоты, нормализацию, название, наценку и фильтрацию по согласованным требованиям. Подключить реализацию через фабрику группы.
- [ ] **8.4. Реализовать группировку аккумуляторов.** Согласовать и проверить правила дублей, сведения складов, выбора предложения и спорных характеристик. Применять только внутри `batteries`.
- [ ] **8.5. Добавить реальные настройки и шаблоны аккумуляторов.** Настроить колонки и стратегии конкретных поставщиков, а также колонки результата для поддерживающих группу шаблонов.
- [ ] **8.6. Проверить полный сценарий двух групп.** На эталонных прайсах одного поставщика разобрать шины/диски и аккумуляторы, получить независимые типизированные списки и сформировать отдельные файлы и общую книгу. Снять запрет из 1.5 только для `batteries` после прохождения сценария; сохранить общую preflight-проверку доступности фабрик, стратегий и преобразователей для всех выбранных групп из 4.5 и 6.2.

## Этап 9. Итоговые проверки

Для каждой задачи с изменениями кода запускать полный набор проверок в порядке CI; критерии конкретной задачи дополняют его. Новые тесты должны проверять контракты и независимость групп, а не повторять устройство реализации.

- [ ] **9.1. Проверить тесты и покрытие:** `uv run pytest` (включая порог 95%).
- [ ] **9.2. Проверить форматирование:** `uv run black --check --diff .`.
- [ ] **9.3. Проверить Ruff:** `uv run ruff check .`.
- [ ] **9.4. Проверить Flake8:** `uv run flake8 .`.
- [ ] **9.5. Проверить типы:** `uv run mypy .`.
- [ ] **9.6. Проверить слои:** `uv run lint-imports`.
- [ ] **9.7. Проверить мёртвый код:** `uv run vulture`.
- [ ] **9.8. Проверить безопасность кода:** `uv run bandit -r src -c pyproject.toml`.
- [ ] **9.9. Проверить зависимости:** `uv run pip-audit`.

## Зависимости этапов

Основная последовательность: 1 → 2 → 3 → 4 → 5 → 6 → 7. Исключение: минимальную тестовую реализацию второй группы из 7.2 подготовить перед 6.4; полную проверку изоляции выполнить на этапе 7. Этап 8 начинается после согласования модели аккумулятора и использует готовые интерфейсы предыдущих этапов. Проверки этапа 9 выполняются после каждой задачи с изменением кода и повторно для итогового результата.

Полная функция готова после этапа 8: поставщик работает с двумя реальными моделями, а шаблон выбирает отдельные файлы или вкладки без смешивания полей и позиций.
