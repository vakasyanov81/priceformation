# Task-25: Единый владелец компонентов обработки строк

**Статус:** реализовано; проверки пройдены.

Продолжение [task-21](./task-21-base-parser-composition.md). Основание — архитектурная проверка текущего кода.

## Проблема

Ссылки на `row_filters`, `enricher` и `pipeline` одновременно хранятся в `BaseParser` и `TireAndDiskHandler`. При создании `RowPipeline` также получает ссылки на фильтры и обогатитель.

В `BaseParser.process()` ссылки из парсера копируются в обработчик перед обработкой строк. Эта синхронизация не обновляет зависимости внутри уже созданного pipeline. Подмена компонента через один из объектов может оставить в других объектах прежнюю ссылку: предварительная обработка и pipeline будут использовать разные экземпляры.

Корень проблемы находится в слое `parsers`: несколько изменяемых точек настройки одного графа зависимостей без единого владельца. Контракты импортов этого не обнаруживают. Это риск рассинхронизации при подмене компонентов; нарушение результата на штатных данных пока не подтверждено.

Основные места:

- `src/parsers/base_parser/base_parser.py`: конструктор и `process()`;
- `src/parsers/base_parser/tire_and_disk_handler.py`: конструктор и `process_rows()`;
- `src/parsers/base_parser/row_pipeline.py`: хранение и использование зависимостей;
- фабрики обработчика и config-driven парсера, тесты подмены коллабораторов.

## Цель и решение

Сделать граф компонентов обработки строк согласованным по построению. Назначить `TireAndDiskHandler` владельцем графа; передавать согласованные зависимости при сборке обработчика. `BaseParser` отвечает за чтение и передачу строк обработчику и не синхронизирует его внутреннее состояние.

Предпочтительный способ настройки — сборка нового обработчика с нужными зависимостями. Проверить текущие вызовы и тесты: если замена после создания действительно нужна приложению, предусмотреть одну явную операцию владельца, которая сохраняет согласованность всех потребителей. Несколько независимых изменяемых точек настройки не сохранять.

## План

1. Через Codegraph найти всех читателей и места присваивания компонентов в парсере, обработчике и pipeline. Отделить потребности приложения от тестовых подмен.
2. Воспроизвести рассинхронизацию минимальным тестом: предварительная обработка и pipeline должны использовать один согласованный набор компонентов. Тест должен падать на исходном коде.
3. Сосредоточить сборку и владение графом в обработчике; убрать копии ссылок и присваивания синхронизации из `BaseParser`.
4. Перевести фабрики и вызывающий код на единый способ настройки. Тесты отдельных компонентов создавать непосредственно с их зависимостями.
5. Проверить неизменность результата разбора и выполнить `just ci-compact` из корня по всему репозиторию.

## Ограничения

- Сохранить порядок фильтрации, обогащения, шагов pipeline и расчёта наценки.
- Сохранить результаты разбора, статистику и диагностику на эталонных данных.
- Не менять модель аккумуляторов и внешние форматы результатов.
- Не включать сюда глобальный контекст окружения, DI-контейнер и логирование доменных исключений: это отдельные причины и задачи.
- Не вводить `__getattr__`, подавления линтеров или обход контрактов слоёв ради совместимости.

## Критерии готовности

- [x] `BaseParser` не хранит отдельные изменяемые копии `row_filters`, `enricher`, `pipeline` и не копирует их в обработчик перед запуском.
- [x] Обработчик и pipeline используют согласованные экземпляры зависимостей.
- [x] Регрессионный тест проверяет причину рассинхронизации и падает до исправления.
- [x] Вызовы и тестовые подмены переведены на выбранный контракт без ослабления проверок поведения.
- [x] Результаты интеграционного разбора сохранены.
- [x] `just ci-compact` завершился с exit 0: все девять проверок, включая покрытие не ниже 95%.
- [x] В итоговом описании указаны причина, новый владелец компонентов и закрепляющий тест.

Коммит — только после отдельного подтверждения пользователя.

## Результат

Причина подтверждена в слое `parsers`: после замены фильтров обработчика
pipeline продолжал вызывать прежний экземпляр. Минимальное воспроизведение
падало с `Expected 'skip_by_min_rest' to have been called once. Called 0 times.`

Единственный владелец — `TireAndDiskHandler`: он хранит один `RowPipeline`,
а предварительная обработка берёт фильтры и обогатитель из этого же графа.
`RowPipeline` — frozen dataclass; ссылка обработчика на него доступна только
для чтения. Настройка выполняется при сборке нового обработчика с готовым
pipeline; стандартные зависимости собирает `make_row_pipeline`.
`BaseParser` больше не хранит копии компонентов и не синхронизирует их.
Фабрика `make_handler` и тестовые подмены используют новый контракт.

Регрессионные тесты в `tests/test_base_parser/test_tire_and_disk_handler.py`:

- `test_handler_builds_consistent_graph` проверяет вызовы одних экземпляров
  фильтров и обогатителя до pipeline и внутри него;
- `test_graph_rejects_independent_replacement` проверяет запрет независимой
  замены pipeline, фильтров, обогатителя, процессора и hooks. Все пять случаев
  дополнительно проверены на исходных классах из `HEAD`: падают с
  `DID NOT RAISE AttributeError`.

`just ci-compact` завершился с exit 0: все девять проверок, включая полный
набор модульных и интеграционных тестов и порог покрытия 95%, прошли.
