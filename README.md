# Формирование прайс-листов

Программа собирает общий прайс-лист из прайс-листов поставщиков шин: названия
позиций, закупочные цены, остатки и другие параметры. Наценка считается
автоматически по заданным правилам. Поведение каждого поставщика описывается
одним JSON-файлом, поэтому новый поставщик добавляется без изменения программы.

## Как запустить

Нужен Python 3.14 и менеджер пакетов [uv](https://docs.astral.sh/uv/).
Установка зависимостей — `uv sync`.

Запуск выполняется из корня проекта (текущий каталог значения не имеет — пути
считаются от файлов проекта):

```
uv run pf              # интерактивное меню
uv run pf parse --json # разбор без меню, ответ в JSON
```

Точка входа называется `priceformation`, есть короткий алиас `pf` — это одно и
то же. Из justfile то же самое: `just run` (меню) и `just run parse --json`.
Готовые скрипты запуска без тестовых зависимостей — `src/run.sh` (Linux) и
`src/run.bat` (Windows).

## Папки и файлы

```
parse_config/                 настройки (не код)
    vendors/<folder>.json     конфиг поставщика, имя файла = имя папки прайсов
    mail.json                 доступ к почтовому ящику и профили поставщиков
    black_list                чёрный список позиций
    manufacturer_aliases.json синонимы брендов
    title_aliases.json        синонимы названий
    doubles.json              исключение дублей в шаблонах результата
    four_tochki_warehouses.json группы складов Форточек для выгрузки по API
    correct-nomenclature.xlsx справочник номенклатуры
    dummy/                    примеры настроек

file_prices/                  входные прайсы и результат
    <folder>/                 прайсы одного поставщика
    result/                   готовые прайс-листы
```

Папка поставщика в `file_prices` совпадает с именем его конфига:
`parse_config/vendors/poshk.json` ↔ `file_prices/poshk/`. Внутри лежат файлы,
подходящие под маски `file_templates` (для Excel — например `price*.xls*`,
для JSON-источников — свои имена, у Запаски `disk.json` / `tire.json`).

## Результат

Готовые файлы складываются в `file_prices/result`:

| Файл | Для чего |
|---|---|
| `price_<дата>.xlsx` | прайс для внутреннего использования (`for_inner`) |
| `price_drom_<дата>.xlsx` | прайс для drom.ru (`for_drom`) |
| `price_full_<дата>.xlsx` | полный прайс (`for_full`, только по явному запросу) |
| `doubles_<дата>.xlsx` | отчёт о дублях (пишется при каждом `parse` и командой `doubles`) |

## Команды

Без аргументов открывается интерактивное меню (пункт `4 — справка` открывает
этот README в постраничном просмотрщике — `less` или `$PAGER` — с подсветкой
заголовков, кода и ссылок). Для сторонних скриптов доступны подкоманды:

- `parse` — разобрать прайсы поставщиков и записать файлы (прайсы и отчёт о дублях);
- `doubles` — разобрать прайсы и записать отчёт о дублях;
- `zapaska_load_api_data` — выгрузить прайсы Запаски по API;
- `four_tochki_load_api_data` — выгрузить шины и диски Форточек по API (в
  `file_prices/four_tochki/tire.json` и `disk.json`; нужен источник `api`; склады подбираются
  по ключевым словам групп из `parse_config/four_tochki_warehouses.json` и выводятся на экран);
- `mim_load_api_data` — выгрузить каталог МИМ по API (`file_prices/mim/price.xlsx`);
- `fetch_mail_prices` — скачать свежие прайсы поставщиков из почты;
- `get_supliers` — вернуть каталог поставщиков:
  `{"1": {"sup_code": "poshk", "sup_title": "Пошк"}}`;
- `get_product_types` — вернуть типы товара, которые priceformation ставит в
  колонку «Тип товара» прайсов (в порядке словаря):
  `{"ok": true, "action": "get_product_types", "types": ["Легковая шина", …]}`;
- `get_vendors` — вернуть поставщиков (файлы конфигов `parse_config/vendors/*.json`) с
  признаком активности, как в интерактивном меню:
  `{"ok": true, "action": "get_vendors", "vendors": [{"folder": "poshk", "name": "Пошк", "enabled": true}]}`;
- `toggle_vendor <folder>` — переключить активность поставщика по папке (имя файла без `.json`)
  и вернуть новое состояние: `{"ok": true, "action": "toggle_vendor", "vendor": {"folder": "poshk", "name": "Пошк", "enabled": false}}`.
  Неизвестная папка — `ok: false` с `error.kind` = `ConfigValidationError`, файлы не меняются;
- `load_supplier_prices` — разложить файлы прайсов по папкам поставщиков:
  `{"1": "/путь/прайс.xls"}`, `{"poshk": "/путь/прайс.xls"}` или список файлов
  `{"4": ["/путь/прайс.xlsx", "/путь/territories.json"]}`. Ключ — ИД
  поставщика или `sup_code`. Допускаются `xls`, `xlsx`, `json` и `zip`-архив с
  такими файлами (вложенные папки архива не важны). Файлы перемещаются в
  `file_prices/<sup_code>/`:
  - имя, подходящее под `file_templates` поставщика (у Запаски `disk.json`,
    `tire.json`) или служебное (`territories.json` у поставщика с
    `warehouse_cities`), сохраняется;
  - остальные `xls`/`xlsx` переименовываются в `price.xls(x)`, следующие — в
    `price_2`, `price_3`, …, если такое имя подходит под маски поставщика;
  - прочие файлы — ошибка, ничего не перемещается.

  Одноимённые файлы заменяются. Если пришли `xls`/`xlsx`, прежние
  Excel-прайсы поставщика удаляются (остальные файлы, например
  `territories.json`, остаются);
- `load_config` — положить файл или папку настроек в `parse_config`: путь к
  `*.json`, `*.xlsx`, `black_list` или к папке с такими файлами. Файлы
  перемещаются с теми же именами (существующие заменяются). Файл из папки
  `vendors/` кладётся в `parse_config/vendors/` — удобно заливать конфиги
  поставщиков.

### Флаги

- `--json` — одна JSON-строка в stdout, логи не печатаются; прайсы пишутся в
  `.jsonl`, рядом — `result_meta.json`;
- `--all-result` — включить в JSON сами позиции разбора (без флага — только
  статистика); сам по себе тоже включает JSON-режим;
- `--clear-previous-result` — очистить `file_prices/result` перед записью;
- `--result-template NAME` — для `parse`: записать только этот шаблон
  (`for_inner`, `for_drom`, `for_full`). Без флага — `for_inner` и `for_drom`
  (`for_full` только явно). Неизвестное имя — ошибка. Отчёт о дублях пишется
  в любом случае.

### Формат ответа

Код выхода: `0` при успехе, `1` при ошибке. Во всех JSON-ответах есть
`ok` и `elapsed_seconds` (секунды). У команд `parse` / `doubles` дополнительно:
`action`, `stats`, `files`, `warnings`, `suppliers`, `disabled_suppliers`,
`positions`, `error`. У остальных команд — только `ok`, `action`, `files`,
`error`.

В `.jsonl` каждая строка — объект с ключами `"1"`, `"2"`, … вместо названий
колонок; расшифровка — в `result_meta.json` в той же папке. Ключи со значением
`null` в строку не пишутся. Повторяющиеся значения заменяются короткими кодами
`"@1"`, `"@2"`, словарь — в `values`.

### Примеры

```
uv run pf parse --json --clear-previous-result
uv run pf parse --json --all-result
uv run pf parse --json --result-template for_drom
uv run pf doubles --json
uv run pf zapaska_load_api_data --json
uv run pf four_tochki_load_api_data --json
uv run pf mim_load_api_data --json
uv run pf fetch_mail_prices --json
uv run pf get_supliers
uv run pf get_product_types
uv run pf get_vendors --json
uv run pf toggle_vendor poshk --json
uv run pf load_supplier_prices='{"poshk": "/full/path/price.xls"}'
uv run pf load_supplier_prices='{"4": ["/full/path/mim.xlsx", "/full/path/territories.json"]}'
uv run pf load_supplier_prices='{"zapaska": "/full/path/zapaska.zip"}'
uv run pf load_config=/full/path/vendors/mim.json
uv run pf load_config=/full/path/settings_dir
```

## Получение прайсов из почты

Команда `fetch_mail_prices` (и «обновить прайсы всех поставщиков») скачивает свежее письмо с прайсом для
каждого поставщика по IMAP и кладёт вложение в `file_prices/<папка>/price.xlsx`.

Настройки — в `parse_config/mail.json`:

```json
{
  "imap": { "host": "imap.timeweb.ru", "port": 993, "folder": "INBOX" },
  "profiles": {
    "pioner": {
      "enabled": 1,
      "sender": "${MAIL_SENDER_PIONER}",
      "subject_keyword": "прайс",
      "attachment_glob": "*.xlsx"
    },
    "poshk": {
      "enabled": 1,
      "sender": "${MAIL_SENDER_POSHK}",
      "sender_is_domain": 1,
      "attachment_glob": "прайс*.xlsx"
    }
  }
}
```

- `imap.folder` — корневая папка (по умолчанию `INBOX`). Письма ищутся в ней и
  во всех вложенных папках (по ответу IMAP `LIST`); из подходящих берётся самое
  свежее по дате письма;
- ключ профиля — папка поставщика в `file_prices`;
- `sender` — точный адрес; при `sender_is_domain: 1` — домен, на который
  оканчивается адрес отправителя;
- `subject_keyword` — подстрока темы (регистр не важен); не задана — тема не
  фильтруется;
- `attachment_glob` — маска имени вложения (регистр не важен). Письмо
  подходит, только если во вложении ровно один файл по маске;
- `link_in_body: 1` — прайс не во вложении, а по ссылке в теле письма. Письмо
  подходит, только если в теле ровно одна ссылка на `.xlsx` (`http`/`https`);
  файл скачивается по ссылке и кладётся в `price.xlsx`. `attachment_glob` в
  таком профиле не нужен. Если скачать не удалось, поставщик пропускается с
  предупреждением;
- `enabled: 0` временно выключает профиль.

Адреса отправителей в файле не хранятся: `"${MAIL_SENDER_PIONER}"` — ссылка на
переменную из `.env` (или окружения), её значение подставляется при чтении настроек.
Так `mail.json` лежит в git, а адреса — только локально. Ссылка `${ИМЯ}` работает в
любой строке `mail.json`; переменная не задана — ошибка с путём до ключа.

Логин и пароль ящика в файле не хранятся: они берутся из `MAIL_LOGIN` /
`MAIL_PASSWORD` (переменные сессии или `.env`, см. `.env.example`), а при
интерактивном запуске недостающее запрашивается у пользователя. В
неинтерактивном режиме (`--json`, cron) отсутствие данных — ошибка.

## Настройки

Все настройки лежат в `parse_config`. Каждый поставщик описывается одним
JSON-файлом; остальные файлы действуют на прайсы всех поставщиков.

- `enabled` в конфиге поставщика включает (`1`) и выключает (`0`) его разбор.
  Выключенные поставщики попадают в `disabled_suppliers`.

## Поставщик — один JSON-файл

Поведение поставщика полностью описывается файлом `parse_config/vendors/<folder>.json`.
Имя файла (без `.json`) совпадает с именем папки поставщика в `file_prices`.

Пример:

```json
{
  "enabled": 1,
  "code": "7",
  "name": "STK",
  "start_row": 12,
  "file_templates": ["price.xlsx"],
  "category": { "strategy": "tire_size_category" },
  "title": { "strategy": "poshk_stk_tire_compose" },
  "pricing": {
    "policy": "map_on_opt",
    "rules": { "markup_rules": [{ "min": 0, "max": 5000, "percent": 0.2 }, { "min": 5000, "max": 99999, "percent": 0.1 }] }
  },
  "sections": [
    { "sheet_indexes": [0], "columns": { "0": "code", "1": "title", "2": "price_opt", "5": "rest_count" } }
  ]
}
```

### Три уровня настроек

Настройка ищется снизу вверх: **секция → поставщик → общие настройки** (`vendors/_common.json`).
Задавать ключ нужно только там, где он отличается от уровня выше:

- объекты (`title`, `category`, `pricing`, `rules`, `behavior`, `columns`) сливаются по ключам — секция может
  задать только `"title": { "strategy": "disk_compose" }`, а остальные ключи `title` возьмёт у поставщика;
- числа, строки и списки заменяются целиком; шкала `markup_rules` тоже заменяется целиком.

### Общие настройки — `vendors/_common.json`

Файлы в `vendors/` с именем на `_` — не поставщики. `_common.json` хранит то, что одинаково у всех:

```json
{
  "title_reference_order": ["four_tochki", "autosnab54_ru", "zapaska", "mim", "stk", "pioner", "poshk"],
  "defaults": {
    "file_templates": ["price*.xls", "price*.xlsx"],
    "category": {
      "size_fields": {
        "Грузовая шина": { "season": "Всесезонная" },
        "Спецшина": { "season": "Всесезонная" }
      }
    },
    "title": { "params_from_title": true },
    "behavior": { "min_rest": 4 }
  }
}
```

- `defaults` — настройки в той же форме, что у поставщика; действуют у всех, пока поставщик не задал своё;
- `title_reference_order` — очередь эталонов названия группы дублей: имена файлов поставщиков, первый — главный
  (см. «Одинаковое название и буквы-двойники»). Поставщик вне списка идёт после всех; неизвестное имя — ошибка.

Файла нет — у поставщиков только их собственные настройки и значения по умолчанию из таблиц ниже.

### Уровень поставщика

| Ключ | Обяз. | Значение |
|---|---|---|
| `enabled` | да | `1` — разбор включён, `0` — выключен |
| `code` | да | внешний ИД каталога (например `1`, `22`); по умолчанию `id` секций |
| `name` | да | название поставщика (по умолчанию для секций) |
| `start_row` | нет | номер первой строки данных, счёт с 1; по умолчанию `1` (для `json` не нужен) |
| `file_templates` | да* | маски файлов прайсов в `file_prices/<folder>/` (общее значение — в `_common.json`) |
| `reader` | нет | `xls` (по умолчанию) или `json` |
| `columns` | нет | маппинг колонок по умолчанию для секций |
| `pricing` | нет | наценки по умолчанию для секций |
| `category`, `title` | нет | стратегии по умолчанию для секций |
| `behavior` | нет | общие переключатели разбора |
| `sections` | да | непустой список секций — по одной на лист/файл |

\* `file_templates` и `columns` обязательны хотя бы на одном уровне: у
поставщика либо у каждой секции.

### Уровень секции

Секция — один лист (для `xls`) или один файл (для `json`). Отсутствующие ключи
берутся у поставщика, объекты дополняются (см. «Три уровня настроек»).

| Ключ | Значение |
|---|---|
| `id` | ИД каталога; по умолчанию `code` поставщика |
| `name` | название; по умолчанию `name` поставщика |
| `start_row` | первая строка данных; по умолчанию у поставщика |
| `file_templates` | маски файлов; по умолчанию у поставщика |
| `sheet_info` | метка листа, добавляется к названию в отчёте |
| `sheet_indexes` | индексы листов xls, счёт с 0; пусто — все листы |
| `columns` | маппинг колонок; **дополняет** маппинг поставщика (общие колонки — у поставщика, свои — в секции) |
| `category`, `title`, `pricing` | дополняют одноимённые слоты поставщика: заданные ключи заменяются, остальные наследуются |

Один поставщик может иметь несколько секций с разными `id` (например Запаска →
`2` диски и `22` шины) или несколько секций с одним `id` (Мим — три вкладки).

### Колонки

`columns` — карта `{"<источник>": "<поле позиции>"}`:

- при `reader: "xls"` ключ — индекс колонки (с 0) строкой: `"1": "title"`;
- при `reader: "json"` ключ — имя ключа исходной JSON-записи: `"cae": "code_art"`;
  если ключи записи совпадают с полями позиции, достаточно списка: `"columns": ["code", "title", "price_opt"]`.

Поле, не указанное в `columns`, остаётся пустым. Основные поля:

```
code  code_man  code_art  title  manufacturer_name  brand  model
season  spike  width  height_percent  diameter  ext_diameter  tire_type
index_load  index_velocity  construction_type  axis  layering  intimacy
camera_type  inscription_on_the_side  run_flat  us_aff_designation
disk_thickness  slot_count  pcd1  pcd2  eet  central_diameter  fastener
disk_type  disk_type_1  color  main_color
price_opt  price_recommended  rest_count  reserve_count  delivery_period
condition  available  type_production
```

### Поведение разбора (`behavior`)

| Ключ | По умолчанию | Значение |
|---|---|---|
| `min_rest` | `4` | минимальный остаток; `0` — отсечка выключена |
| `rest` | `count` | `count` — остаток как есть; `minus_reserve` — `rest_count - reserve_count` |
| `skip_markup_without_opt` | `false` | не наценять строки без закупа |
| `zero_rest_without_category` | `false` | без категории остаток обнуляется |
| `collect_missing_recommended` | `false` | собирать строки без РРЦ в отчёт |
| `find_manufacturer_on_enrich` | `true` | искать производителя при обогащении |
| `pipeline` | `["title","min_rest","category","markup"]` | порядок шагов разбора строки |

`pipeline` принимает только шаги `title`, `min_rest`, `category`, `markup`.

## Стратегии разбора

Стратегия задаётся именем в слоте; неизвестное имя — ошибка конфига с путём до
ключа.

### `category` — тип товара строки

| Стратегия | Параметры | Что делает |
|---|---|---|
| `none` | — | не менять категорию из прайса (по умолчанию) |
| `fixed` | `value` | одна категория для всех строк секции |
| `title_keywords` | `map`, `default` | по вхождению ключевого слова в название (порядок ключей в `map` важен) |
| `field_map` | `field`, `map`, `default` | по значению поля через карту (регистр и пробелы нормализуются) |
| `column_canonical` | `unknown_skip` | канонизировать категорию из колонки; неизвестные → пусто |
| `header_rows` | `zero_rest_categories`, `map`, `default` | категория из строк-заголовков (первый кусок канонизируется встроенной картой: `автошина` → `Автошина` и т.п., `map` из конфига дополняет её); у перечисленных категорий остаток обнуляется |
| `tire_size_category` | — | тип по размеру и маркерам в названии: `Грузовая шина`, `Легкогрузовая шина`, `Легковая шина`, `Спецшина`, а также `Автокамера`, `Диск`, `Ободная лента` |

Дополнительно в слоте `category`:

- `size_fields` — карта «тип, определённый по размеру названия → поля позиции».
  Тип считается независимо от стратегии слота: так все поставщики получают сезон
  «Всесезонная» у грузовых и спецшин (правило задано в `_common.json`). Незаполненные поля получают значения из конфига,
  уже проставленные не перетираются;
- `calculate_type` — включить независимое определение типа: заявленный
  стратегией тип сохраняется для сверки, а в `type_production` пишется
  вычисленный (см. «Определение типа товара»). По умолчанию выключено.

### `title` — подготовка названия

| Стратегия | Параметры | Что делает |
|---|---|---|
| `default` | — | оставить название как есть (по умолчанию) |
| `normalize_title` | — | схлопнуть пробелы, десятичную запятую привести к точке |
| `normalize_size_chunks` | `fallback_brand` | нормализация названий Пошка: срезать обёртки «Шина»/«а/п», `*`→`x`, «н.с.N»→`PRN` |
| `poshk_stk_tire_compose` | `fallback_brand`, `camera_by_kind` | собрать название STK/Пошка: размер, бренд, модель, нагрузка/скорость, PR, камера, назначение; «Шина» без бренда — как `normalize_size_chunks`; `camera_by_kind` — карта «слово вида шины → камерность», добавляется в название, если камерности в нём нет (Пошк: `автошина`/`спецшина`/`сельхозшина` → `TT`, `*покрышка` → `TL`) |
| `tire_compose` | `variant` | собрать название шины: `mim_simple`, `mim_truck`, `four_tochki` |
| `disk_compose` | `variant` | собрать название диска: `four_tochki` |
| `fill_fields_from_title` | — | разобрать размер и модель из названия, само название не менять (Автоснабжение) |
| `manufacturer_from_category` | — | производитель из раздела-категории (Пионер) |

Флаги слота:

- `aliases: true` — дополнительно заменить название по `title_aliases.json`;
- `markers` — карта «подстрока названия → поля позиции»: если название содержит
  маркер, незаполненные поля получают заданные значения (регистр не важен).
  Например, у Пошка «шип» означает зиму и шипованую шину.

## Ценообразование

Наценка поставщика задаётся слотом `pricing`; у секции может быть свой
`pricing`, который переопределяет поставщика.

Политики (`policy`):

- `base` — наценка по карте `rules` (по умолчанию);
- `identity` — без наценки (цена в прайсе уже отпускная, например Автоснабжение);
- `map_on_opt` — наценка по карте `%` от закупа;
- `recommended_or_map` — РРЦ, если она есть, иначе карта `%`;
- `recommended_range` — как `recommended_or_map`, но с диапазоном процента по
  категории (`category_markup_ranges`) и абсолютным полом (Форточки);
- `percent_by_threshold` — фиксированный процент в зависимости от закупа:
  `rules.threshold`, `rules.low`, `rules.high` (наценка Мим, грузовая вкладка).

Шкала `markup_rules` — список правил: диапазон закупочных цен (`min`/`max`) и
процент наценки (`percent`, доля: `0.2` = 20 %):

```json
"pricing": {
  "policy": "base",
  "rules": {
    "markup_rules": [
      { "min": 0, "max": 201, "percent": 0.7 },
      { "min": 200, "max": 301, "percent": 0.5 },
      { "min": 300, "max": 501, "percent": 0.4 }
    ],
    "min_recommended_percent_markup": 0.14,
    "max_recommended_percent_markup": 0.27,
    "absolute_markup_rules": { "min_absolute_markup": 200, "markup_percent": 1.5 }
  }
}
```

Примечания:

- правила проверяются по порядку, срабатывает первое, в диапазон которого попал закуп;
- если для закупочной цены нет подходящего диапазона, наценка идёт по
  минимальному проценту из `markup_rules`;
- прежняя форма шкалы — объект «имя → правило» (`"rule_70": {…}`) — тоже читается.

Необязательные настройки:

- `min_recommended_percent_markup` / `max_recommended_percent_markup` —
  минимальная и максимальная допустимая наценка по РРЦ;
- `replace_small_recommended` — подменять ли РРЦ картой `%`, когда наценка по
  РРЦ меньше минимума (`false` по умолчанию — если РРЦ есть, её не трогают);
- `absolute_markup_rules.mode` — что делать, если рублёвая маржа меньше
  `min_absolute_markup`: `multiplier` (по умолчанию) — цена = `закуп * markup_percent`;
  `delta` — цена = `закуп + min_absolute_markup`;
- `category_markup_ranges` — допустимый диапазон процента по категории товара
  (политика `recommended_range`), ключ — имя типа (`Грузовая шина`, `Диск`, …),
  значение — `{min, max}`.

### Примеры поставщиков

- **Пошк** — `map_on_opt`, `min_rest: 0`, категория `tire_size_category`,
  название `poshk_stk_tire_compose` с маркером «шип»;
- **Мим** — три секции; легковые и диски — `base`, грузовая вкладка —
  `percent_by_threshold`;
  выгрузка по API (`mim_load_api_data`) пишет `file_prices/mim/price.xlsx` и список складов
  `territories.json`. Склады берутся из колонки «Территория» (`warehouse_name`) и «ID Территории»
  (`warehouse_id`). `behavior.warehouse_cities` (например, `["Новосибирск"]`) оставляет остатки
  только на складах этих городов: город — слово целиком в названии или адресе склада из
  `territories.json` (улица «Новосибирская» не подходит), остаток прочих обнуляется. Пустой список —
  без фильтра; `behavior.api_types` (по умолчанию `[1, 3, 4]`) — категории выгрузки по API: 1 шины, 2 диски, 3 грузовые шины, 4 грузовые диски, 5 секретки, 6 крепёж, 7 прочее; `behavior.order_from_warehouse_name: true` берёт из названия склада «Под заказ» (в «Наличие»)
  и срок «от N д.» (в «Срок доставки»), например «НС.Под заказ от 4д.»; нет `territories.json` или в нём нет такого города — ошибка разбора МИМ;
- **Форточки** — `recommended_range`: диапазоны по категориям и абсолютный пол
  `mode: delta`, `+500 ₽`; названия `tire_compose(four_tochki)` и
  `disk_compose(four_tochki)`. Источник выбирается полем `source`:
  `xlsx` (по умолчанию) — xlsx-прайс из `file_prices/four_tochki/price*.xlsx`;
  `api` — блок `api` с JSON-секциями для `tire.json` / `disk.json`, которые
  пишет `four_tochki_load_api_data`. Блок `api` накладывается на настройки поставщика
  вместо файловых ключей (`start_row`, `file_templates`, `reader`, `columns`, `sections`): наценка и
  вариант названия задаются один раз на уровне поставщика и действуют в обоих режимах. В режиме `api` на каждый склад API — отдельная
  строка прайса. Склады задаются не ID, а группами в `parse_config/four_tochki_warehouses.json`:
  перед выгрузкой запрашивается справочник складов API (`GetWarehouses`), и склад попадает в
  выгрузку, если его название содержит одно из ключевых слов группы (без учёта регистра).
  Склад, подходящий под несколько групп, относится к первой из них; не подходящий ни под одну —
  в запрос не попадает. Подобранные склады выводятся на экран по группам; группа без складов —
  предупреждение, ни одного склада — ошибка. У группы задаются:
  - `name` — имя группы (обязательно, уникально);
  - `keywords` — ключевые слова в названии склада (`["Новосибирск", "НСБ"]`);
  - `merge` — `true`: склады группы сводятся в прайсе дрома в одну строку на позицию.
    Одинаковая цена — остатки складываются; разные — берётся наименьшая цена с её остатком,
    остальные остатки не учитываются;
  - `available` и `delivery_period` — наличие и срок доставки для строк складов группы (у
    Томска и Новокузнецка — «Под заказ», 5 дней; без них — «В наличии» по умолчанию).

  В колонке «Склад» своего прайса выводится название склада из API.
  ```json
  {"groups": [
    {"name": "novosibirsk", "keywords": ["Новосибирск", "НСБ"], "merge": true},
    {"name": "order", "keywords": ["Томск", "Новокузнецк"], "available": "Под заказ", "delivery_period": 5}
  ]}
  ```
  В своём прайсе позиции из разных складов выводятся отдельными строками со своими ценами и
  остатками. Название из API
  разбирается по параметрам (`params_from_title` + `params_first`: размер, индексы, камера, диск без слова «Диск»),
  а затем собирается теми же правилами, что и название из xlsx (`tire_compose` / `disk_compose`, вариант `four_tochki`);
- **Запаска** — `reader: json`, `base` с порогом РРЦ 8 %,
  `replace_small_recommended: true`, абсолютный пол `mode: delta`, `+150 ₽`;
  название шин собирается из полей (`title.compose`, см. ниже);
- **Автоснабжение** — `identity`: цена в прайсе уже отпускная; название шин собирается из полей (`title.compose`);
- **STK** — все настройки (включая наценку) в своём файле.

Слот `title.compose: true` (вместе с `params_from_title`; Запаска (шины), Пионер, Автоснабжение) пересобирает
название шины из полей позиции в каноническом порядке `размер бренд модель нагрузка+скорость [XL] [<N>PR] [камера]
[M+S] [3PMSF] [RunFlat] [ось]` вместо текста поставщика. Тот же порядок у `tire_compose` (Форточки, Мим) и
`poshk_stk_tire_compose` (Пошк, STK). Бренд — производитель, найденный по алиасам в тексте поставщика.
`XL`, `TL`/`TT`, `M+S`, `3PMSF` и ось (`Рулевая`, `Ведущая`, `Прицепная`, `Универсальная`, `Карьерная`) остаются
в названии; шип, `FR`, описание в скобках в название не входят. Завод (`НкШЗ`, `ОШЗ`, `ЯШЗ`) и год выпуска
(`2023г.в.`) выделяются из названия в колонки `Завод` и `Год выпуска` общего прайса.
Диск (Запаска (диски)) собирается тем же шаблоном, что у Форточек: `<ширина>x<диаметр> <отверстия>x<PCD> ET<вылет> <DIA>
<Цвет> <бренд> <модель> [хвост]`; DIA без буквы `D`, цвет с заглавной буквы, хвост (толщина, усиление, завод в скобках)
берётся из текста поставщика. Камера и ободная лента (Пошк, STK, Пионер, Автоснабжение) собираются как
`Камера|Ободная лента <размер> [бренд] [модель]`: размер `11.00-20` / `12.5/80-18` / `1200x500-508`, модель — `ГК-145`,
`УК-13М`, `300-508А` (лента с такой моделью пишет её вместо размера); `СВК`, `(25)`, `Китай` в название не входят.
Кольцо не меняется. Шина, у которой размер не разобрался, диск без ширины, диаметра, бренда или модели и камера без
размера остаются текстом поставщика, а итоговый лог показывает число таких позиций
(«Название шины, диска, камеры или ленты не собрано из полей»).

### Одинаковое название и буквы-двойники

Кириллические двойники (`ТТ`, `R16С`, `86Н`, `ЕТ35`) исправляются при разборе, до сборки названия
(`parsers/strategies/homoglyphs.py`): технические токены — всегда латиница, в словах модели — алфавит, которого в
смешанной части больше; русские модели (`НК-241`, `Кама-310`) не меняются. Неисправимые случаи (`Каzантип`) пишутся
только в файл лога и считаются в статистике поставщика.

Внутри группы дублей у всех позиций одно название. Эталон — позиция с самой полной моделью, среди равных —
поставщик раньше в очереди `title_reference_order` (`vendors/_common.json`: Форточки, Автоснабжение, Запаска,
Мим, STK, Пионер, Пошк). Название эталона берётся как есть, к нему
добавляются `XL`, камерность, `M+S`, `3PMSF` и ось, которые есть хотя бы у одной позиции группы.

## Дубли

Дубли — одна и та же позиция у разных поставщиков (или у одного поставщика
несколько раз). Позиции сравниваются по параметрам названия: тип товара,
размер, индексы, модель с учётом алиасов брендов, камерность, RunFlat,
параметры диска и т. п. Совпавшие позиции получают общий номер группы
(«Группа по параметрам»); в группе одна позиция помечается «Главный дубль»,
остальные — «Дубль»; явный конфликт шипа, сезона или XL пишется в «Спорная».

**Отчёт о дублях** (`doubles_<дата>.xlsx`) формируется автоматически при каждом
разборе прайсов (`parse`, пункт меню `1 — сформировать общий прайс`), а также отдельной
командой `doubles`. В отчёт попадают только позиции, у которых есть дубль.
«Главный дубль» в отчёте выбирается своим правилом (обычный товар важнее
уценки, затем свежая партия, затем меньшая цена) и не определяет, какая строка
останется в шаблоне — для этого правила ниже.

### Исключение дублей в шаблоне

Файл `parse_config/doubles.json` (необязательный: если файла нет, дубли не
исключаются нигде):

```json
{
  "exclude_in_templates": ["for_drom"],
  "priority_suppliers": ["Автоснабжение"]
}
```

- `exclude_in_templates` — шаблоны результата (`for_inner`, `for_drom`,
  `for_full`), в которых из каждой группы дублей остаётся **одна строка**.
  Неизвестное имя шаблона — ошибка настройки. В остальных шаблонах и в отчёте
  о дублях строки не исключаются.
- `priority_suppliers` — приоритетные поставщики по порядку важности; имя —
  как `name` в конфиге поставщика (`parse_config/vendors/*.json`), а если у
  секции свой `name` (например, «Форточки (шины, API)») — как у секции.

Какая строка группы остаётся — правила применяются по порядку, каждое сужает
выбор; если правилу не соответствует ни одна строка, оно пропускается:

1. **Приоритетный поставщик.** Если в группе есть позиция поставщика из
   `priority_suppliers` (Автоснабжение), выбор идёт только среди его позиций —
   даже если у других дешевле или они в наличии. Поставщики проверяются по
   порядку списка: первый найденный выигрывает.
2. **В наличии важнее, чем под заказ.** Если есть позиция в наличии, позиции
   под заказ игнорируются. Под заказ — позиция, у которой в «Наличии» есть
   слово «заказ» (например, «Под заказ» у складов Форточек); пустое «Наличие» —
   в наличии.
3. **Наименьшая цена.** Среди оставшихся берётся позиция с наименьшей ценой с
   наценкой. Если наименьшую цену дают несколько позиций, их **остатки
   складываются** в одну строку (данные — от первой из них).

Дополнительно: позиция без остатка не выбирается, пока в группе есть позиция с
остатком (шаблон дрома такие строки всё равно не пишет — иначе позиция
пропала бы из прайса целиком).

В шаблоне дрома склады одной группы поставщика сначала сводятся в одну строку
(см. группы складов Форточек), и только потом исключаются дубли.

Пример. В группе: Пошк — 5 000 ₽, 4 шт., в наличии; Форточки — 4 800 ₽, 8 шт.,
под заказ; Мим — 5 000 ₽, 2 шт., в наличии. Автоснабжения нет → под заказ
(Форточки) отбрасывается → у Пошка и Мима одинаковая цена → в прайс дрома
уходит одна строка: 5 000 ₽, 6 шт. Если бы в группе была позиция
Автоснабжения — осталась бы она.

## Чёрный список

Файл `parse_config/black_list`. Действует на всех поставщиков. Каждая строка —
одно правило, пустые строки пропускаются.

- **Точное название** — строка без `*` исключает позицию, если наименование
  совпадает целиком;
- **Маска** — при наличии `*` это шаблон без учёта регистра, `*` означает любую
  последовательность символов. Например `*некондиция*` — фраза где угодно в
  названии, `восстановленная*` — название начинается с этой фразы.

## Алиасы производителей (брендов)

Файл `parse_config/manufacturer_aliases.json`. Действует на всех поставщиков.
Поставщики пишут один бренд по-разному («Michelin» / «Мишелин», «BF Goodrich» /
«BFGoodrich», «Белшина» / «БШК»), а файл задаёт каноническое имя и варианты.

Ключ — как бренд должен выглядеть в результате, значение — массив написаний,
встречающихся у поставщиков:

```json
{
  "Michelin": ["Мишелин"],
  "BF Goodrich": ["БФ гудрич", "BFGoodrich"],
  "Белшина": ["БШК", "Belshina"],
  "Sunrise": []
}
```

Пустой массив `[]` — у бренда нет альтернативных написаний; само каноническое
имя всё равно ищется в названии. Если бренда нет в файле, из названия он не
извлекается, а в колонке «Бренд» остаётся то, что дал поставщик.

Поиск без учёта регистра, по отдельным словам (в начале/конце названия или с
пробелами по краям); более длинные имена проверяются раньше коротких. Файл
должен оставаться валидным JSON, после правки — перезапуск разбора.

## Определение типа товара

Тип товара (`type_production`) определяется по названию и параметрам строки по
общепринятым в отрасли принципам. Колонка типа у поставщика при этом не источник
истины, а слабый ориентир для сверки.

Типы товара: `Легковая шина`, `Легкогрузовая шина`, `Грузовая шина`,
`Спецшина`, `Мотошина`, `Автокамера`, `Ободная лента`, `Уплотнительное кольцо`,
`Диск`. Сезон, шипы, бренд, цвет, `TL`/`TT`, `XL`, `RunFlat` — это атрибуты, а
не отдельные типы.

Порядок определения (первое совпадение выигрывает):

1. Сначала отсекаются нешинные позиции по ключевому слову: кольцо → камера →
   лента → диск. Это делается первым, потому что у камер и лент тоже бывают
   размеры, похожие на шинные.
2. Если это шина — ищется размер. Размер — самый устойчивый признак: он почти
   всегда присутствует и отделяет легковые от грузовых и спецшин.
3. Тип определяется независимо по названию и параметрам:
   - спецтехника (сельхоз, карьер, погрузчик, маркеры «клюшка», «волна»,
     «цельнолитая» и др.) → `Спецшина`;
   - мотоциклетный размер или маркеры → `Мотошина`;
   - большой диаметр, высокая слойность, «рулевая/ведущая/прицепная» ось →
     `Грузовая шина`;
   - пометки `C`/`LT`/`CP`, фургонные модели (`Van`, `Cargo`, …) →
     `Легкогрузовая шина`;
   - всё остальное → `Легковая шина`.

Правило про категорию поставщика: тип всегда вычисляется заново по названию и
параметрам. Колонка поставщика применяется только после этого — для
перекрёстной проверки. При расхождении приоритет у вычисленного типа,
расхождение фиксируется в логе. Если тип у поставщика не указан или не
распознан, позиция всё равно получает тип и не пропускается.

Работа независимого определения включается ключом `calculate_type: true` в слоте
`category` (например, у Мима и Пионера). Если он выключен, тип берётся из
стратегии слота (`fixed`, `tire_size_category`, `header_rows` и др.).

## Как добавить поставщика

1. Создайте `parse_config/vendors/<folder>.json` — имя файла равно имени папки
   в `file_prices` (готовый файл можно залить командой `load_config`).
2. Заполните уровень поставщика: `enabled`, `code`, `name`, `start_row`;
   `file_templates`, `reader` и `behavior` — только если они отличаются от `_common.json`.
   Чтобы название поставщика участвовало в выборе эталона группы дублей, добавьте имя файла
   в `title_reference_order` (`_common.json`).
3. Опишите хотя бы одну секцию с `columns` (индексы колонок Excel) и стратегиями
   `category` / `title`.
4. Задайте наценку в `pricing` (или политику `identity`, если цена уже
   отпускная).
5. Положите прайсы в `file_prices/<folder>/` и перезапустите разбор.

Если нужно поведение, которого нет среди готовых стратегий, — только оно требует
кода (новая именованная стратегия).

## Переменные окружения

Файл `.env` (шаблон — `.env.example`):

- `ZAPASKA_API_LOGIN` / `ZAPASKA_API_PASSWORD` — доступ к API Запаски;
- `FOUR_TOCHKI_API_LOGIN` / `FOUR_TOCHKI_API_PASSWORD` — доступ к API Форточек;
  `FOUR_TOCHKI_API_HOST` — необязательный адрес сервиса (можно указать WSDL-адрес
  из инструкции, он приводится к адресу сервиса);
- `MIM_API_TOKEN` — токен доступа к API МИМ; `MIM_API_HOST` — необязательный адрес сервиса
  (категории выгрузки — в `vendors/mim.json`, `behavior.api_types`);
- `MAIL_LOGIN` / `MAIL_PASSWORD` — доступ к почтовому ящику для
  `fetch_mail_prices`.

## Планы развития

- У номенклатуры поставщика нужен статус «активна/неактивна»: когда позиция
  исчезает из прайса или остаток становится нулевым, в базе её помечают
  неактивной; если позиция уже есть — обновляются цена и остатки.
- Переход на работу через базу данных и веб-интерфейс: загрузка общего прайса в
  базу, ручная правка номенклатуры и сведение дублей, наценка по правилам из
  настроек, формирование общего прайса и прайса для дрома из базы.
- Вынести наценку для Пионера в настройки.
- Наценка в разрезе принадлежности шины (грузовая/легковая/спецшина).
